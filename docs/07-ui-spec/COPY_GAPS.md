## 0. 도출한 톤 규칙

D에는 톤·문체 절이 없다. 그래서 아래 규칙은 D §4-3·§6-1·§6-2·§6-3의 정본 문구에서 뽑았다. 모든 확정안이 이 규칙을 따른다.

1. 상태를 알리는 문장은 합니다체로 쓴다. 예: 「연결이 끊겼습니다」, 「삭제된 메시지입니다」.
2. 사용자에게 무언가를 요청할 때는 「~해 주세요」로 쓴다. 예: 「다시 로그인해 주세요」, 「잠시 후 다시 시도해 주세요」.
3. 빈 상태는 「~해 보세요」로 쓴다. 예: 「첫 메시지를 남겨 보세요」.
4. 오류는 원인 1문장 + 행동 1개로 쓴다(D §6-1). 사용자를 탓하는 표현은 쓰지 않는다. 「잘못 입력하셨습니다」 대신 「맞지 않습니다」·「확인해 주세요」를 쓴다.
5. 문장부호는 정본을 따른다.
   - 두 문장 이상인 안내는 마침표로 끝낸다.
   - 한 줄짜리 상태 표시·빈 상태·라벨에는 마침표를 찍지 않는다(예: 「잠시 후 다시 시도해 주세요」, 「첫 메시지를 남겨 보세요」).
   - 진행 중 상태는 「…」로 끝낸다.
6. 단정을 피한다. 결과를 모르면 「확인 중」으로 쓰고, 「저장되지 않았습니다」처럼 단정하지 않는다(D §4-3 피하는 표현).
7. 용어는 D §4-3 정본을 쓴다.
   - 「공간」은 채널·DM 목록만 가리킨다. 인스턴스 전체를 부르는 말로 쓰지 않는다.
   - D §4-3 피하는 표현 목록의 단어는 쓰지 않는다.
8. 이모지는 쓰지 않는다. 아이콘은 Lucide 글리프 + 텍스트로 쓴다(D §2-1 D3·D5).

## 1. 로그인 (CMP-19 `LoginForm`, SCR-01)

### G-01 자격 증명 오류 문구 ★
- 위치: `apps/web/src/features/auth/LoginForm.tsx` — 응답이 429가 아닌 4xx일 때(서버 `401 invalid_credentials`, `apps/server/src/modules/auth/routes.ts:31`). 지금은 문구 없이 폼만 유지한다. U §2-9 「자격 증명 오류」 행, U §8 Q-1.
- 확정안: 「로그인할 수 없습니다. 이메일과 비밀번호를 확인해 주세요.」 (`role="alert"`)
- 근거:
  - D §6-2 CMP-19: 구체 원인을 드러내지 않고 같은 문구를 쓴다.
  - D §10-2 S1-5: 비활성 계정의 재로그인도 같은 문구다.
  - T §5(l.138): 계정 존재를 드러내지 않는 동일 오류.
  - 첫 문장은 결과만 말하고 원인을 단정하지 않는다. 그래서 비밀번호 틀림·없는 계정·비활성 계정 셋 다에 거짓 없이 맞는다. 시도 횟수나 15분 같은 제한 수치는 넣지 않는다(U §2-9 제한 행: "화면에 표시하지 않음").
- 대안: 「이메일 또는 비밀번호가 맞지 않습니다.」 — 더 익숙한 표현이지만, 비활성 계정에는 사실과 다른 문장이 된다.
- ★: 권장.

### G-02 로그인 네트워크 오류 + 「다시 시도」 ★
- 위치: `LoginForm.tsx` `catch` 분기(응답 없음). 지금은 문구 없음.
- 확정안:
  - 문구: 「서버에 연결하지 못했습니다. 네트워크를 확인한 뒤 다시 시도해 주세요.」 (`role="alert"`)
  - 버튼: 「다시 시도」. 입력한 이메일·비밀번호를 그대로 두고 같은 요청을 다시 보낸다. 기존 「로그인」 버튼으로 다시 보내도 된다. 다만 D §6-1 오류 상태 규칙은 「다시 시도」 버튼을 명시한다.
- 근거: D §6-1 오류(원인 1문장 + **다시 시도**, 네트워크 오류·타임아웃은 다시 시도 가능), D §4-3 연결 상태 문구의 어휘(「연결」).
- 대안: 버튼 없이 「서버에 연결하지 못했습니다. 잠시 후 다시 로그인해 주세요.」 문구만 두고, 「로그인」 버튼으로 다시 보낸다.
- ★: 권장.

### G-03 로그인 5xx ★
- 위치: `LoginForm.tsx` — 응답 5xx. 지금은 `result.status`가 429가 아니어서 문구 없이 폼만 유지한다.
- 확정안: 「서버에 문제가 생겨 로그인하지 못했습니다. 잠시 후 다시 시도해 주세요.」 + 「다시 시도」
- 근거: D §6-1(5xx는 다시 시도 가능), 톤 규칙 4.
- 대안: G-02와 같은 문구를 쓴다(원인 구분 없음).
- ★: 권장.

### G-04 로그인 400 (입력 형식) ★
- 위치: `LoginForm.tsx` — `400 invalid_request`(`auth/routes.ts:28`, 스키마 불일치). 브라우저 `type="email" required`가 대부분 막아 주므로 드물다.
- 확정안: 「입력 형식을 처리할 수 없습니다. 이메일 주소를 확인해 주세요.」 버튼은 없다.
- 근거: D §6-1(400은 입력을 고쳐야 하므로 버튼 대신 안내만).
- 대안: G-01 문구를 그대로 쓴다(형식 오류와 자격 증명 오류를 구분하지 않음).
- ★: 권장.

### G-05 로그인 화면 제목·안내문 ★
- 위치: `LoginForm.tsx` 폼 위. 지금은 렌더하지 않는다(`features/auth/index.ts` 주석).
- 확정안:
  - 제목(`h1`): 「로그인」
  - 안내문: 「초대받은 계정의 이메일과 비밀번호를 입력해 주세요.」
- 근거:
  - D §4-2: 로그인 화면은 `/login`.
  - D §4-3: 「공간」·「워크스페이스」를 인스턴스 이름으로 쓰지 않는다.
  - 제목에 앱 이름을 넣지 않으면 G-17·G-18 개명과 무관해진다.
  - 계정은 초대로만 생긴다(T §5 l.131, 원격 가입 없음). 그래서 안내문에 「초대받은」을 넣어 가입 경로를 찾지 않게 한다.
- 대안: 제목 「로그인」만 두고 안내문 없음.
- ★: 권장.

## 2. 초대 수락 (CMP-19 `InviteAccept`, SCR-02)

### G-06 초대 화면 제목·안내문 ★
- 위치: `apps/web/src/features/auth/InviteAccept.tsx` 폼 위. 지금은 렌더하지 않는다.
- 확정안:
  - 제목(`h1`): 「초대 수락」
  - 안내문: 「계정을 만들면 바로 참여할 수 있습니다. 이메일·비밀번호·표시 이름을 입력해 주세요.」
- 근거: D §10-1 SCR-02 화면명 「초대 수락」, D §10-2 S1-2(입력 후 `/`로 이동).
- 대안: 제목 「초대받은 계정 만들기」.
- ★: 권장.

### G-07 「표시 이름」 라벨 + 보조 문구 ★
- 위치: `apps/web/src/LiveApp.tsx:29` `DISPLAY_NAME_LABEL = '표시 이름'`(임시), `InviteAccept.tsx` 표시 이름 입력.
- 확정안:
  - 라벨: 「표시 이름」(현재 값 유지)
  - 보조 문구(`aria-describedby`): 「다른 멤버에게 보이는 이름입니다. 64자까지 입력할 수 있습니다.」
- 근거:
  - 서버 계약 `display_name`은 trim 후 1–64자다(`packages/shared/src/members.ts:8`).
  - 상한 안내 형식은 D §6-2 CMP-11 「4,000자까지 입력할 수 있습니다」를 따른다.
  - 「이름」만 쓰면 실명 입력을 요구하는 것처럼 읽힌다.
- 대안: 라벨 「이름」, 보조 문구 없음.
- ★: 권장.

### G-08 비밀번호 입력 보조 문구 (사전 안내) ★
- 위치: `InviteAccept.tsx` 비밀번호 입력(`autoComplete="new-password"`). 지금은 없다.
- 확정안: 「12자 이상 128자 이하로 입력해 주세요.」 (`aria-describedby`)
- 근거:
  - T §5-1 S9(l.169): 길이는 12–128자(code point)이고, 그 밖의 조합 규칙은 없다.
  - 정책 위반은 G-09 오류로 돌아온다. 미리 알려 주면 G-09를 볼 일이 줄어든다(D §6-1 400 「입력 수정 필요」의 예방).
- 대안: 보조 문구 없이 G-09 오류로만 안내한다.
- ★: 권장.

### G-09 초대 수락 `password_policy` 오류 ★
- 위치: `InviteAccept.tsx` — `400 password_policy`(`apps/server/src/modules/members/routes.ts:50`). 지금은 폼만 유지하고 문구가 없다(W-10c Codex r3 #1).
- 확정안: 「비밀번호 길이가 맞지 않습니다. 12자 이상 128자 이하로 입력해 주세요.」 (`role="alert"`, 비밀번호 입력에 `aria-invalid="true"`) 버튼 없음.
- 근거: D §6-1(400은 안내만), T §5-1 S9(12–128자). 정책 위반은 토큰을 소비하지 않으므로 고친 뒤 같은 폼으로 다시 수락할 수 있다(`members/routes.ts:47` 주석).
- 대안: G-08 보조 문구를 오류 색·`aria-invalid`로 강조만 하고 별도 문장은 두지 않는다.
- ★: 권장.

### G-10 초대 수락 `invalid_request` 오류 ★
- 위치: `InviteAccept.tsx` — `400 invalid_request`(스키마 불일치: 이메일 형식, 표시 이름 비었음·64자 초과 등). 서버는 어느 필드인지 알려 주지 않는다.
- 확정안: 「입력 내용을 처리할 수 없습니다. 이메일 형식과 표시 이름(1–64자)을 확인해 주세요.」 버튼 없음.
- 근거: D §6-1(400 안내만). 필드를 특정할 수 없으므로 검사 대상 두 가지를 모두 적는다(`members.ts:7-9`).
- 대안: 「입력 내용을 확인해 주세요」 한 줄.
- ★: 권장.

### G-11 초대 수락 네트워크 오류 ★
- 위치: `InviteAccept.tsx` `catch` 분기. U §2-9 「네트워크 오류」 행(`ErrorState` + 「다시 시도」), U §8 I-5(메모리 토큰으로 재시도).
- 확정안: 「서버에 연결하지 못했습니다. 입력한 내용은 그대로 있으니 다시 시도해 주세요.」 + 「다시 시도」
- 근거: D §6-1(네트워크 오류는 다시 시도 가능), D §10-1 SCR-02 「네트워크 오류」 상태. 해시는 이미 지워졌다. 그래서 새로 고침하면 토큰이 사라진다는 점을 고려해, 이 화면에서 바로 다시 시도하도록 유도한다.
- 대안: 「서버에 연결하지 못했습니다. 다시 시도해 주세요.」 (입력 보존 언급 없음)
- ★: 권장.
- 주의: 응답만 잃었을 뿐 서버가 이미 수락했다면, 다시 시도한 요청은 `invite_invalid`(사용됨)로 돌아온다. 이 경우의 처리는 G-13에 적었다.

### G-12 초대 수락 5xx ★
- 위치: `InviteAccept.tsx` — 응답 5xx. 지금은 폼만 유지한다.
- 확정안: 「서버에 문제가 생겨 초대를 수락하지 못했습니다. 잠시 후 다시 시도해 주세요.」 + 「다시 시도」
- 근거: D §6-1(5xx는 다시 시도 가능).
- 대안: G-11과 같은 문구를 쓴다.
- ★: 권장.

### G-13 「사용할 수 없는 초대」 보조 안내 (결정 필요)
- 위치: `InviteAccept.tsx` `INVITE_UNUSABLE_TEXT` 아래. 정본 문구 「이 초대 링크는 더 이상 사용할 수 없습니다」는 바꾸지 않는다.
- 확정안: 정본 문구 아래에 보조 문장 1개와 링크 1개를 둔다.
  - 보조 문장: 「이미 계정을 만들었다면 로그인해 주세요.」
  - 링크: 「로그인」 → `/login`
- 근거:
  - D §6-1: 빈·오류 상태에는 가능하면 행동 1개를 둔다.
  - 서버는 만료·사용됨·폐기·이미 있는 이메일을 같은 응답(`invite_invalid`)으로 돌려준다(`members/routes.ts:47`, T §5 S3·NC-20).
  - 그래서 G-11 재시도로 이미 가입된 사람도 이 화면을 보게 된다.
- 대안: 보조 문장 없이 「로그인」 링크만 둔다. 또는 지금처럼 아무 행동도 두지 않는다(D §6-2 정본 그대로).
- ★: 없음. "구분하지 않는다"는 정본 원칙(D §6-2 CMP-19)을 벗어나는지 판단이 필요하다. 보조 문장은 원인을 구분하지 않는 일반 안내라서, 권장 쪽으로 기운다.

## 3. PWA 설치 안내·앱 이름 (CMP-20, SCR-07, manifest)

## 6. 수치 (U §8 Q-12·Q-13)

### G-37 WS 재연결 백오프 (Q-12) ★
- 위치: `apps/web/src/data/realtime.ts:29-36`. 현재 구현은 `BACKOFF_BASE_MS = 1_000`, `BACKOFF_MAX_MS = 30_000`, `delay = min(30s, 1s × 2^attempt)`이고 지터는 없다. 정본 값은 없다(U §5-2 C4).
- 확정안: 현재 값을 정본으로 올린다.
  1. 초기 간격 1초, 배수 2, 상한 30초. 재시도 간격은 1·2·4·8·16·30·30…초다.
  2. 시도 횟수 상한은 없다. 「다시 연결 중…」 배너는 계속 유지하고, 끊김 판정은 `navigator.onLine`·HTTP 연속 2회 실패(네트워크 오류·게이트웨이 응답 502/503/504)로만 한다(D §6-4, W-16 F-8).
  3. WS가 열리면 시도 횟수를 0으로 되돌린다.
  4. `online` 이벤트나 전경 복귀(`visibilitychange` visible)가 오면 대기 중인 타이머를 취소하고 즉시 1회 시도한 뒤 시도 횟수를 0으로 되돌린다. 이 항목은 현재 구현에 없는 추가 제안이다.
- 근거:
  - 상한 30초는 서버 heartbeat 25초(T §7 l.200)보다 조금 길다. 그래서 서버가 죽은 연결을 정리하는 주기와 비슷한 간격으로 다시 붙는다.
  - 사용자는 1명이고 기기는 몇 대뿐이라 재연결 폭주 위험이 낮다. 그래서 지터를 기본값으로 넣지 않는다(추정).
  - 복귀 즉시 시도는 D §6-4·U §5-2 C8(전경 복귀 시 catch-up)과 맞다.
- 대안: 상한을 15초로 낮추고 0–20% 지터를 넣는다. 모바일 체감 복구는 빨라지지만 배터리·요청 수가 늘어난다.
- ★: 권장. 결정 주체는 TRD 저자다(U §8 Q-12). 수치는 미측정 제안값이고, QA-FR-SYNC-07에서 확인한다.

### G-38 클라이언트 측 heartbeat 감지 (Q-13, 결정 필요)
- 위치: `realtime.ts`(현재 없음). U §5-3: 서버가 죽은 연결을 정리하기까지 최대 약 50초 동안 「연결됨」이 보일 수 있다.
- 확정안: 클라이언트가 마지막 수신 프레임 후 25초 동안 아무 프레임도 받지 못하면 ping을 1회 보낸다. 그 뒤 10초 안에 응답이 없으면 소켓을 닫고 C4 「다시 연결 중…」으로 간다. 최악 감지 시간은 약 35초다(산술).
- 근거: T §7 heartbeat 25초(같은 주기에 맞춤), U §5-3 D2 항목. ping 프레임 형식이 T §4 WS 계약에 있는지는 확인하지 않았다.
- 대안: 두지 않는다. 서버 정리(약 50초)와 `navigator.onLine`·HTTP 오류에만 맡긴다.
- ★: 없음. WS 프레임 계약 변경이 따르므로 TRD 저자가 결정한다.

- 위치: 문서 행·칩의 형식 표지(U §2-13). 색이 아닌 텍스트로 형식을 알린다(FR-CLIENT-07).
- 확정안: 서버 판정 mime 기준 — 「PDF」 / 「Word」(`.docx`·`.docm`·`.doc`) / 「Excel」(`.xlsx`·`.xlsm`·`.xls`) / 「PowerPoint」(`.pptx`·`.pptm`·`.ppt`) / 「한글」(`.hwp`·`.hwpx`).
- 근거: ADR-002 §4-1 형식 이름 그대로. 형식 이름 표기일 뿐 각 제품의 아이콘·색·로고는 쓰지 않는다(아이콘은 Lucide `file-text` 하나, CLEANROOM 2–4절·D §2-2 취지).
- 대안: 확장자 대문자(「DOCX」·「HWPX」) — 확장자는 파일명 끝에 이미 항상 보이므로(U §2-13 말줄임 규칙) 중복이라 택하지 않았다.
- ★: 권장.

### G-60 「매크로 포함」 표지 ★
- 위치: 문서 행(`has_macros = true`), U §2-13.
- 확정안: 「매크로 포함」
- 근거: ADR-002 §4-3 1(「매크로 포함」 경고 표지를 텍스트로, 문구는 COPY_GAPS 추가 후 결정). 라벨이라 마침표 없음(톤 규칙 5). 위험 단정·공포 표현 없이 사실만.
- 대안: 「매크로 포함 — 열기 전에 확인하세요」 — compact 행에서 두 줄이 되고, 받기를 막지 않기로 한 결정(「받는다」)과 어조가 맞지 않아 택하지 않았다.
- ★: 권장.

### G-61 문서 만료 자리표시자 (재사용) ★
- 위치: 문서 행 `expired = true`.
- 확정안(재사용): 형식 표지 + 파일명 + 「만료된 첨부입니다」(`ATTACHMENT_COPY.expired`). 「받기」 버튼 없음.
- 근거: FR-OPS-05 ⑤와 같은 규칙(ADR-002 §4-3 5). 이미지·오디오 만료와 같은 문구라 학습 비용 0.
- 대안: Claude-Fable §5-2 「보관 기간이 지나 삭제된 파일입니다」 — 기존 첨부 문구와 갈라져 택하지 않았다.
- ★: 권장.

### G-62 「받기」 버튼과 접근 이름 ★
- 위치: 문서 행 오른쪽 버튼(`download` 아이콘 + 텍스트).
- 확정안:
  - 보이는 텍스트: 「받기」
  - 접근 이름: 「{전체 파일명} 받기, {형식}, {크기}」 — 매크로 포함이면 끝에 「, 매크로 포함」 (예: 「예산.xlsm 받기, Excel, 1.2MB, 매크로 포함」)
- 근거: Claude-Fable §5-2 「받기」. 화면의 파일명은 말줄임될 수 있어 전체 파일명을 접근 이름으로 제공한다(U §2-13). 이름 구분자는 G-36 「, 」 관례.
- 대안: 「다운로드」 — 외래어보다 짧은 고유어를 택했다. Fable의 「받는 중…」·「받지 못했습니다. 다시 시도」는 일반 링크 다운로드(UI-D5)라 쓰지 않는다.
- ★: 권장.

## 15. 로그인한 기기 (CMP-22 `SessionList`, U §2-14, ADR-002 1c)

- 상태: **★ Designer 초안**(2026-11-13, p2s1-ui-spec 레인, 사후 조정 가능). 구현 시 `apps/web/src/ui/copy.ts`에 `SESSION_LIST_COPY`로 넣는다.
- 용어: 화면 문구는 「세션」 대신 「기기」·「로그아웃」을 쓴다. 401 공통 문구 「세션이 종료되었습니다…」(D §4-3)는 바꾸지 않는다.

### G-63 화면 제목·진입 버튼 이름 ★
- 위치: 사이드바 계정 카드 아이콘 버튼(`smartphone`, 「로그아웃」 옆) 이름, `/settings/sessions` 화면 제목, 목록 `aria-label`.
- 확정안: 「로그인한 기기」
- 근거: P FR-AUTH-04 「기기별 세션 목록」. 사용자가 보는 대상은 기기다. 세 자리에 같은 문구를 써서 진입점과 도착 화면이 맞는다(G-44 「봇 제거」 진입점 = 제목 구조와 같음).
- 대안: 「기기 관리」 — 할 수 있는 일이 로그아웃뿐이라 과장이라 택하지 않았다.
- ★: 권장.

### G-64 이 기기 표지 ★
- 위치: `current = true` 행의 텍스트 표지.
- 확정안: 「이 기기」
- 근거: Claude-Fable §5-2. 색 외 텍스트 구분(FR-CLIENT-07). 라벨이라 마침표 없음.
- 대안: 「현재 기기」 — 의미 같고 한 글자 길어 택하지 않았다.
- ★: 권장.

### G-65 기기 라벨 형식·라벨 없음 ★
- 위치: 행 1줄째.
- 확정안:
  - 라벨 있음: 서버가 로그인 시 만든 거친 라벨 그대로, 형식 「{기기 종류} · {브라우저}」(예: 「iPhone · Safari」, 「Mac · Chrome」). 웹은 가공하지 않는다.
  - 라벨 없음(`device_label` null): 「알 수 없는 기기」. 같은 이름의 행이 둘 이상이면 버튼 접근 이름 끝에 「, 마지막 사용 {시각}」을 붙여 구분한다.
- 근거: ADR-002 C-4 ★(거친 라벨만), Claude-Fable §4-5(원시 UA·IP 미저장). 「알 수 없는 사용자」(G-51)와 같은 중립 폴백.
- 대안: 라벨 없을 때 「이전 로그인」 — 기기 정보가 없다는 사실을 흐려 택하지 않았다.
- ★: 권장.

### G-66 마지막 사용 시각 ★
- 위치: 행 2줄째(`last_seen_at`).
- 확정안: 「마지막 사용 {시각}」 — {시각}은 오늘이면 「오늘 오후 3:12」, 어제면 「어제 오후 3:12」, 그 전은 「2026-11-02」(날짜만). `Intl.DateTimeFormat('ko-KR')`(D §7-5), 「오늘」·「어제」는 G-42 재사용.
- 근거: Claude-Fable §5-2 「마지막 사용 <시각>」. 날짜 형식은 CMP-10 `DateSeparator`와 같다.
- 대안: 상대 시각(「3분 전」) — 시간이 흐를 때 다시 그려야 하고 기존 화면에 상대 시각 표기가 없어 택하지 않았다.
- ★: 권장.

### G-67 로그아웃 버튼 ★
- 위치: 행 오른쪽 버튼.
- 확정안: 다른 기기 행 「로그아웃」(접근 이름 「{기기 라벨} 로그아웃」), 이 기기 행 「이 기기에서 로그아웃」.
- 근거: 기존 사이드바 「로그아웃」(`SIDEBAR_COPY.logout`, copy.ts:211)과 같은 동사. Claude-Fable §5-2 「이 기기에서 로그아웃」. 행 안이라 대상이 보이므로 짧게, 접근 이름에는 대상을 넣는다(G-27 구조).
- 대안: 「종료」·「연결 끊기」 — 사용자에게 익숙한 「로그아웃」과 다른 말을 늘려 택하지 않았다.
- ★: 권장.

### G-68 다른 기기 없음 ★
- 위치: 목록에 이 기기만 있을 때 이 기기 행 아래 `EmptyState`.
- 확정안: 「다른 기기에서 로그인하지 않았습니다」
- 근거: 사실 서술 한 줄, 행동 버튼 없음(할 일이 없다). 마침표 없음(톤 규칙 5). 「~해 보세요」(규칙 3)는 권할 행동이 없어 쓰지 않는다.
- 대안: 「이 기기에서만 로그인되어 있습니다」 — 의미 같음, 「다른 기기」로 화면 목적을 바로 드러내는 쪽을 택했다.
- ★: 권장.

### G-69 기기 로그아웃 확인 Dialog ★
- 위치: CMP-18 Dialog(다른 기기 로그아웃 확인, 새 용도 9번째).
- 확정안:
  - 제목: 「기기 로그아웃」
  - 본문: 「{기기 라벨} 기기가 5초 안에 로그아웃되고 그 기기의 알림도 꺼집니다. 그 기기에서 다시 쓰려면 다시 로그인해야 합니다.」
  - 버튼: 「로그아웃」(주 동작, danger) / 「취소」
- 근거: T §5 :149(revoke 후 5초 안 WS close), T :66(세션 폐기 시 push 구독 CASCADE 삭제). 멤버 비활성화 Dialog 문구(「…5초 안에 로그아웃되며…」, D §4-3)와 같은 구조.
- 대안: 본문 1문장 「이 기기를 로그아웃할까요?」 — 알림이 꺼진다는 결과가 빠져 택하지 않았다.
- ★: 권장.

### G-70 로그아웃 실패 ★
- 위치: 확인 Dialog 안 오류.
- 확정안: 「로그아웃하지 못했습니다.」 + 원인 1문장(`failureText` — `ERROR_COPY` 재사용: network·timeout·server·rateLimited·badRequest·notFound)
- 근거: G-47(「봇을 추가하지 못했습니다.」 + 원인) 구조와 같음.
- 대안: 원인 없이 한 문장 — 다시 시도할지 판단할 수 없어 택하지 않았다.
- ★: 권장.

### G-71 로그아웃 완료 알림 ★
- 위치: StatusRegion(시각적으로 숨김), 행 제거 직후.
- 확정안: 「{기기 라벨} 기기를 로그아웃했습니다」
- 근거: 행이 사라지는 변화는 포커스 이동만으로 알 수 없다(WCAG 4.1.3, D §7-1). 한 줄 상태라 마침표 없음.
- 대안: 알림 없음 — 스크린리더 사용자가 결과를 모르게 되어 택하지 않았다.
- ★: 권장.

### G-72 목록 오류·시간 초과 (재사용) ★
- 위치: 목록 요청 실패 `ErrorState`.
- 확정안(재사용): `ERROR_COPY.network`·`server`·`rateLimited` 원인 1문장, 시간 초과(20초 상한)면 `ERROR_COPY.timeout` 「서버 응답이 늦어 확인하지 못했습니다.」 + 「다시 시도」.
- 근거: G-19 공통 사전, PR #31 C1 `timedOut` 매핑(`apps/web/src/features/spaces/failure.ts:5-12`).
- 대안: 화면 전용 문구 — 공통 사전으로 충분해 택하지 않았다.
- ★: 권장.
