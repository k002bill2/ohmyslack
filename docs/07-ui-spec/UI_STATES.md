## 2. 컴포넌트별 상태표

### 2-0. 읽는 법과 공통 진입 조건

모든 표의 열은 **상태 / 진입 조건 / 표시(문구는 「」) / 가능한 동작 / 탈출 조건**이다. 진입 조건의 HTTP 상태 코드 의미는 T §3 마지막 문단 정본이다.

| 코드·신호 | 의미(T §3·§4) | UI 공통 처리(D §6-1) |
|---|---|---|
| 2xx | 성공. 메시지 생성은 `id`·`seq`·`change_id`·`client_message_id` 포함(T §3 `POST …/messages`, R3.1) | 기본 상태 |
| 네트워크 오류·타임아웃·5xx | 응답 없음 또는 일반 오류 | 오류 상태 + 「다시 시도」 버튼 |
| 400 | 입력·범위 오류 | 버튼 대신 안내(입력 수정 필요) |
| 401 | 인증 없음 또는 비활성 계정 | 메모리 비움 → `/login`, 「세션이 종료되었습니다. 다시 로그인해 주세요.」(D §4-3, §6-4) |
| 403 | 참여자가 관리자 권한·타인 메시지 쓰기 요청 | 권한 없음 안내, 버튼 없음 |
| 404 | 비멤버의 대화 단위 자원 접근(존재 은폐) | 대상 없음 안내(403과 화면에서 구분하지 않음, D §10-2 S3) |
| 409 | 멱등 충돌(같은 ID·다른 내용) | 「다시 작성」 안내, 새 `client_message_id`(D §6-1) |
| 410 | sync cursor 만료 | ConnectionBanner 「최신 상태 확인 중…」 유지, snapshot 절차(D §6-4) |
| 429 | 로그인 제한(T §3·§5) | CMP-19 「잠시 후 다시 시도해 주세요」 |
| `navigator.onLine === false` | 브라우저 오프라인 | ConnectionBanner 「연결이 끊겼습니다」 상태(§5) |
| WS close | 알림 경로 단절(T §4: WS는 best-effort) | ConnectionBanner 「다시 연결 중…」, HTTP는 그대로 보냄(D §6-3 전이 2) |

### 2-1. 공통 5상태 프리미티브 — CMP-17 `EmptyState` / `ErrorState` / `Skeleton` (D §6-1)

| 상태 | 진입 조건 | 표시 | 가능한 동작 | 탈출 조건 |
|---|---|---|---|---|
| 기본 | 데이터 있음 | 컴포넌트 고유 렌더 | 컴포넌트별 | — |
| 로딩 | 첫 요청 발송 후 응답 전 | `Skeleton`: 텍스트 줄 3개, `aria-busy="true"`. **스피너 단독 금지**. 문구 없음 | 없음 | 2xx → 기본/빈, 오류 → 오류 |
| 빈 | 2xx + 항목 0개 | `EmptyState`: Lucide 아이콘(muted) + 1문장 + 가능하면 행동 버튼 1개. 문장은 컴포넌트별 정본 문구(아래 표) | 행동 버튼 | 데이터 생김 → 기본 |
| 오류(재시도 가능) | 네트워크 오류·타임아웃·5xx·429(대기 후) | `ErrorState`: 경고 아이콘 + 원인 1문장 — (정본 없음 → §8 Q-1) + 「다시 시도」, `role="alert"`. 경고 아이콘 이름은 D §3-4 ⚠️(빌드 시 확정) | 「다시 시도」 = 같은 요청 재발송 | 2xx → 기본 |
| 오류(재시도 불가) | 400 / 401 / 403 / 404 / 409 | 버튼 대신 안내만. 401은 `/login` 이동, 403·404는 권한 없음·대상 없음 + 목록 새로 고침 안내, 409는 「다시 작성」 안내 | 안내된 동작만 | 사용자가 다른 화면으로 이동 |
| 오프라인 | `navigator.onLine === false` 또는 WS 단절 | **컴포넌트는 표시하지 않는다.** 상위 CMP-15가 표시. 쓰기 동작을 비활성화하지 않음 | 모두 | §5 상태 머신 |

**NewMessagesDivider**: 「여기부터 새 메시지」. 진입 = 본문 읽음 커서(`last_read_seq`) 다음 원문이 화면 목록에 있을 때 1개. 보이면 스크롤 앵커. 미읽음 점프 라우트 `/c/:conversationId#m-:seq`(D §4-2). 참여 직후에는 서버가 커서를 `joined_seq`로 초기화하므로 그리지 않는다(D §10-2 FR-CONV-02 1). catch-up 중에는 위치 갱신을 보류한다.

### 2-5. CMP-07 `MessageItem` · CMP-08 `MessageBody` · CMP-26–29 — 메시지 상태 (정본: D §6-3, P FR-MSG-02·03, T §2·§3·§4)

**판정 원칙(D §2-1 D4, §6-3).** 저장 판정은 HTTP 결과로 한다. WS는 알림 경로다. Jarvis 결정(★)에 따라 T R3.1이 `client_message_id`를 전송 응답과 `message.created`에 넣었으므로, 「저장 여부 확인 중」의 **자동 해소를 기본 경로**로 하고 수동 「다시 시도」는 fallback으로 둔다(D §6-3 전이 4와 다른 점은 §8 I-3).

**대응 키:** 로컬 대기 항목과 서버 메시지의 일치는 `(conversation_id, author_id = 나, client_message_id)` 3개 값으로 판정한다. 이는 T §2의 멱등 unique key와 같다. `client_message_id` 단독으로 판정하지 않는다.

**전이 규칙(D §6-3 1–4 + Jarvis 결정)**

1. 「저장 확인」은 연결 상태로 되돌리지 않는다.
2. 「다시 연결 중…」(WS만 끊김)에서도 HTTP 전송을 그대로 보내고 HTTP 결과로 판정한다.
3. 전송 직후 작성기는 **즉시 비워지고** 본문은 「전송 중」 항목으로 옮겨진다. 늦게 온 ACK는 작성기를 건드리지 않는다.
4. 「저장 여부 확인 중」은 아래 중 하나가 일어날 때까지 유지한다. ① 대응 키가 같은 `message.created` 수신(자동, 기본 경로) ② 사용자의 「다시 시도」 결과 ③ 사용자의 로컬 삭제.
5. 같은 메시지가 HTTP 응답과 `message.created`로 두 번 와도 **항목은 1개**다. 대응 키(위)와 `change_id`로 중복을 제거한다(T §4).
6. 「전송 중」 상태에서 대응 키가 같은 `message.created`가 먼저 오면, 중복 행을 만들지 않고 항목에 "서버 커밋 이벤트 수신" 표식만 남긴다. 이후 HTTP가 응답 없이 끝나면 「저장 여부 확인 중」을 거치지 않고 「저장 확인」으로 간다. 이벤트만으로 「전송 중」을 즉시 「저장 확인」으로 바꿀지는 D4와 충돌하므로 **결정 필요(§8 Q-3)** — 결정 전 구현은 HTTP 응답을 기다린다.

**주의(자동 해소의 한계)**

- T R3.1은 `client_message_id`를 **전송 응답과 `message.created`에만** 명시했다. `GET /api/sync`·이력 응답 projection의 포함 여부는 T에 없다(§8 Q-2). WS가 끊긴 동안 커밋된 메시지는 catch-up으로 들어오므로, 그 항목은 자동 해소되지 않을 수 있다. 이때는 수동 「다시 시도」(멱등)가 fallback이다.
- 대기 항목은 **화면 메모리에만** 있다(P 원칙 2, T §6 지속 발신 큐 없음). 전체 새로고침·앱 종료 시 사라진다. 서버가 이미 저장했다면 새로고침 후 이력에 정상 메시지로 나타난다.
- **오프라인 자동 재전송**(2026-11-17 영환님 결정): 전송 시점 `navigator.onLine === false`로 실패한 항목, 오프라인에서 「다시 시도」한 항목, `onLine === false`인 동안 응답 없이 끝난 「저장 여부 확인 중」 항목에 표식을 남긴다. `online` 이벤트 때 표식 항목을 **생성 순서대로 하나씩**, **같은 `client_message_id`·본문·`thread_root_id`** 로 **한 번** 다시 보낸다(서버 멱등이 중복을 막는다). 재전송이 온라인에서 다시 실패하면 표식이 지워져 수동 「다시 시도」로 돌아간다(반복 없음). 온라인 상태의 4xx·5xx·네트워크 오류, 400·409(「다시 작성」), 삭제한 항목, 로그아웃 뒤는 보내지 않는다.

**MessageBody**(D §6-2 CMP-08, T §5): 텍스트 노드로만 렌더, HTML 미실행. 자동 링크는 `https`·`http`만, 그 외 스킴은 일반 텍스트. 링크 `rel="noopener noreferrer"`. 코드 블록은 `--font-mono`, `overflow-x: auto`. 한글 줄바꿈 `word-break: keep-all; overflow-wrap: anywhere;`(D §3-2). 본문 자체의 고유 상태는 없고, 코드 블록 복사 버튼만 아래 상태를 가진다.

- **코드 블록 「복사」 버튼(2026-11-22):** 코드 블록(```…```)마다 버튼 1개. 인라인 코드·다른 블록에는 없다. 버튼은 `pre` 밖·래퍼(`.msg-code-block`) 안 오른쪽 위에 고정되어 가로 스크롤과 함께 밀리지 않고, `pre` 텍스트에 섞이지 않는다. 복사 내용은 블록 원문 그대로(공백·줄바꿈·들여쓰기 보존).
  - 상태: **기본** 보이는 글자 「복사」(`aria-label="코드 복사"`) → **복사됨** 성공 시 버튼 글자 「복사됨」 1600ms 후 기본 복귀(연속 성공이면 마지막 성공부터 1600ms를 다시 센다) / **실패**(클립보드 없음·거부) 버튼 글자 「복사 실패」 1600ms 후 기본 복귀. 결과 안내는 늘 렌더되는 `role=status`(보조기술 전용, 시각적으로 숨김)의 글자만 바꿔 알리고(성공 「복사됨」, 실패 「복사하지 못했습니다」) 포커스는 옮기지 않는다. 안내는 레이아웃을 밀지 않는다.
  - 배치: 버튼은 최소 폭(가장 긴 글자 「복사 실패」 기준)을 갖고, 버튼이 있는 블록의 `pre`는 그 폭 + 간격만큼 오른쪽 여백을 둔다 — 긴 한 줄을 끝까지 스크롤하면 마지막 글자가 버튼 왼쪽에 보인다. 버튼·안내 글자는 드래그 선택에 섞이지 않는다(`user-select: none`).
  - 노출: 마우스 환경(`hover: hover`)은 코드 블록 hover 또는 포커스(`:focus-within`)일 때만 보이고(투명 처리 — 키보드로 닿음), 터치 환경(`hover: none`)은 항상 보인다. 터치 환경의 히트 영역은 보이는 크기를 바꾸지 않고 투명 확장으로 44px 이상(위·오른쪽은 블록 안쪽 여백까지만, 가로 넘침 없음). 버튼의 클릭·키 입력은 메시지 단축키·메뉴·액션 시트를 열지 않는다. 지정 테스트 `apps/web/test/conversation/code-copy.test.tsx`·`code-copy-css.test.ts`.

- **제한된 서식(P FR-MSG-10, ADR-001 §3-f):** 굵게·인라인 코드(`--font-mono`)·글머리/번호 목록·제목 1–3단계·`[텍스트](http/https URL)` 링크만 서식으로 렌더한다. 제목은 본문 대비 **시각 크기 단계만** 두고 제목 태그를 남용하지 않는다(크기 단계 → §8 Q-H6). 그 외(기울임·취소선·인용·표)와 닫히지 않은 기호, 허용 밖 스킴 링크는 원문 기호 그대로 일반 텍스트. 렌더는 계속 텍스트 노드만(HTML 미생성, 위 원칙 유지). 지정 테스트 `apps/web/test/conversation/render-format.test.tsx`(DD 6-2 FR-MSG-10).
- **`/`로 시작하는 본문(P FR-BOT-06):** 표시도 원문 그대로다. 봇 승인 요청 안의 명령 문구는 인라인 코드로 보인다(작성기 쪽 규칙은 §2-6).

### 2-13. CMP-32 `DocumentAttachment` — 문서 첨부 (ADR-002 §3 1b·§4, P FR-OPS-09, 문구 COPY_GAPS G-53–G-62)

- 범위: PDF·Word·Excel·PowerPoint·한글(구형 Office 포함)을 **다운로드 전용**으로 주고받는다(ADR-002 §4-1, 인라인 미리보기 없음). 형식 판정·상한·보존은 서버 정본(ADR-002 §4-2·§4-3 → TRD §6-1 개정 대상, REPORT ④)이며 이 절은 값을 인용만 한다: 문서 25 MiB/파일, 이미지 10 MiB 유지, 메시지당 4개(T §6-1), 보존 90일.
- 데이터원: 첨부 projection의 `filename`·`has_macros`(계약 T §6-1-1 (3)·(5), 1b 구현 대기). 현재 구현 projection(T §4 `attachments[{id,mime,byte_size,…,expires_at,expired}]`)에는 둘 다 없다.
- 텍스트 계열(T §6-1-1 (1) R3.6, ADR-002 §4-3 Q12 ★): `.txt`·`.md`·`.csv`도 이 절의 문서 칩·문서 행·「[문서]」(G-58)·만료 규칙을 그대로 따른다. `has_macros`는 항상 false라 「매크로 포함」 표지가 붙지 않는다. 형식 표지는 「TXT」·「MD」·「CSV」(G-59).
- 봇이 보낸 문서와 사람이 보낸 문서는 **같은 행**으로 그린다. 봇 구분은 작성자 이름 옆 CMP-26 배지뿐이며 문서 행에는 봇 전용 표시·색이 없다(UI-D9).

- **전체 파일명 접근 방법:** ① 「받기」 버튼 접근 이름(스크린리더·음성 제어) ② 정밀 포인터(medium·wide)에서 파일명 요소 `title` ③ 터치(iPhone)는 `title`이 보이지 않으므로 compact에서 이름부를 **최대 2줄**까지 보이고 그 뒤에만 말줄임한다(확장자부 분리 규칙 유지). 그래도 잘리면 받은 파일의 이름이 최종 확인 수단이다. 툴팁·길게 누르기 전용 UI는 만들지 않는다.
- **배치(폭별):** 390px(compact)·834px(medium)·1440px(wide) 배치와 간격·토큰은 D §6-5. 요약: 390 = 파일명 블록(형식 표지 + 파일명, 이름부 최대 2줄) + 메타 줄(크기·「매크로 포함」) + 오른쪽 「받기」 44×44 이상 / 834·1440 = 1줄(표지·파일명·크기·표지) + 「받기」, 행 최대 폭 D §6-5.
- **붙여넣기 첨부(작성기):** 입력란에 이미지·파일을 붙여넣으면(⌘V/Ctrl+V) 「파일 첨부」와 같은 경로(첨부 초안 저장소 → 칩·업로드)로 붙는다. 새 화면·문구 없음. 첨부가 비활성인 작성기, 클립보드에 파일이 없을 때, 파일과 함께 비어 있지 않은 `text/plain`이 있을 때(표 복사 등)는 가로채지 않고 기본 텍스트 붙여넣기(텍스트 우선). 예외: `text/plain`이 공백뿐이거나 줄 단위 목록이 붙여넣은 파일들의 원래 이름과 같으면(유니코드 정규화(NFC) 후 비교, 줄바꿈 CR/LF/CRLF; Finder 파일 복사가 파일명을 함께 싣는 경우) 첨부한다.
  파일은 `clipboardData.files` 우선, 비면 `items`의 `kind = file`. 허용 형식·용량·개수는 기존 규칙 그대로(G-54·G-55 실패 칩, 남은 자리만큼 자름). 이름이 없거나 확장자가 허용 밖인 허용 이미지 MIME은 `image.<ext>`로 이름만 보정한다. 첨부가 가득 찼으면 기본 동작만 막고 추가하지 않는다(버튼 비활성과 같은 상태). 드래그 앤 드롭은 범위 밖.
- **스레드 답글 작성기:** 본문 작성기와 같은 첨부 경로(「파일 첨부」 버튼·칩·실패 알림·붙여넣기, 업로드 대상 = 스레드가 속한 대화). 첨부 초안 키 = 스레드 root id(글 초안과 같은 규칙, 본문 작성기 칩과 섞이지 않음). 스레드를 닫거나 다른 원문으로 바꾸면 그 키의 진행 중 업로드를 끊고 칩을 버린다.
- 지정 테스트: DD 6-2에 FR-OPS-09 행이 없다 → 구현 레인이 DD에 행을 추가한 뒤 이름을 정한다(테스트 이름을 이 문서가 새로 정하지 않음, CLAUDE.md). 확인 항목은 REPORT UI-AC-01–UI-AC-11.

### 5-3. ⚖️-D2 — UI 배너 조건과 TRD heartbeat의 관계

| HTTP 네트워크 오류·게이트웨이 응답(502/503/504) 연속 2회 | D §6-4(제안값) + W-16 F-8(리버스 프록시 뒤 서버 다운은 502로 옴. 앱 서버는 502–504를 내지 않음) | **클라이언트** 배너 판정 | → C6 「연결이 끊겼습니다」 |
| `navigator.onLine` | D §6-4 | 클라이언트 | → C6 즉시 |

- 두 값은 **서로 다른 것을 판정한다.** heartbeat는 "WS가 살아 있나"(알림 경로), HTTP 연속 오류는 "서버에 닿나"(저장 경로)다. WS만 죽으면 「다시 연결 중…」이고 전송은 계속 HTTP로 판정한다.
- 최악의 경우 서버가 죽은 연결을 정리하기까지 약 50초(25초 × 2) 걸릴 수 있다는 것은 산술 추정이다. 그동안 클라이언트는 「연결됨」을 보일 수 있다. 클라이언트 측 heartbeat 감지(ping 송신·타임아웃)를 둘지는 정본에 없다 → §8 Q-13. 체감 정합은 `QA-FR-SYNC-07`에서 확인한다(D ⚖️-D2).
