## 2. 컴포넌트별 상태표

### 2-0. 읽는 법과 공통 진입 조건

모든 표의 열은 **상태 / 진입 조건 / 표시(문구는 「」) / 가능한 동작 / 탈출 조건**이다. 진입 조건의 HTTP 상태 코드 의미는 T §3 마지막 문단 정본이다.

| 코드·신호 | 의미(T §3·§4) | UI 공통 처리(D §6-1) |
|---|---|---|
| 2xx | 성공. 메시지 생성은 `id`·`seq`·`change_id`·`client_message_id` 포함(T §3 `POST …/messages`, R3.1) | 기본 상태 |
| 네트워크 오류·타임아웃·5xx | 응답 없음 또는 일반 오류 | 오류 상태 + 「다시 시도」 버튼 |
| 400 | 입력·범위 오류 | 버튼 대신 안내(입력 수정 필요) |
| 401 | 인증 없음 또는 비활성 계정 | 메모리 비움 → `/login`, 「세션이 종료되었습니다. 다시 로그인해 주세요.」(D §4-3, §6-4) |
| 403 | 참여자가 관리자 권한·타인 메시지 쓰기 요청 | 권한 없음 안내, 버튼 없음 |
| 404 | 비멤버의 대화 단위 자원 접근(존재 은폐) | 대상 없음 안내(403과 화면에서 구분하지 않음, D §10-2 S3) |
| 409 | 멱등 충돌(같은 ID·다른 내용) | 「다시 작성」 안내, 새 `client_message_id`(D §6-1) |
| 410 | sync cursor 만료 | ConnectionBanner 「최신 상태 확인 중…」 유지, snapshot 절차(D §6-4) |
| 429 | 로그인 제한(T §3·§5) | CMP-19 「잠시 후 다시 시도해 주세요」 |
| `navigator.onLine === false` | 브라우저 오프라인 | ConnectionBanner 「연결이 끊겼습니다」 상태(§5) |
| WS close | 알림 경로 단절(T §4: WS는 best-effort) | ConnectionBanner 「다시 연결 중…」, HTTP는 그대로 보냄(D §6-3 전이 2) |

### 2-1. 공통 5상태 프리미티브 — CMP-17 `EmptyState` / `ErrorState` / `Skeleton` (D §6-1)

| 상태 | 진입 조건 | 표시 | 가능한 동작 | 탈출 조건 |
|---|---|---|---|---|
| 기본 | 데이터 있음 | 컴포넌트 고유 렌더 | 컴포넌트별 | — |
| 로딩 | 첫 요청 발송 후 응답 전 | `Skeleton`: 텍스트 줄 3개, `aria-busy="true"`. **스피너 단독 금지**. 문구 없음 | 없음 | 2xx → 기본/빈, 오류 → 오류 |
| 빈 | 2xx + 항목 0개 | `EmptyState`: Lucide 아이콘(muted) + 1문장 + 가능하면 행동 버튼 1개. 문장은 컴포넌트별 정본 문구(아래 표) | 행동 버튼 | 데이터 생김 → 기본 |
| 오류(재시도 가능) | 네트워크 오류·타임아웃·5xx·429(대기 후) | `ErrorState`: 경고 아이콘 + 원인 1문장 — (정본 없음 → §8 Q-1) + 「다시 시도」, `role="alert"`. 경고 아이콘 이름은 D §3-4 ⚠️(빌드 시 확정) | 「다시 시도」 = 같은 요청 재발송 | 2xx → 기본 |
| 오류(재시도 불가) | 400 / 401 / 403 / 404 / 409 | 버튼 대신 안내만. 401은 `/login` 이동, 403·404는 권한 없음·대상 없음 + 목록 새로 고침 안내, 409는 「다시 작성」 안내 | 안내된 동작만 | 사용자가 다른 화면으로 이동 |
| 오프라인 | `navigator.onLine === false` 또는 WS 단절 | **컴포넌트는 표시하지 않는다.** 상위 CMP-15가 표시. 쓰기 동작을 비활성화하지 않음 | 모두 | §5 상태 머신 |

### 2-5. CMP-07 `MessageItem` · CMP-08 `MessageBody` — 메시지 상태 (정본: D §6-3, P FR-MSG-02·03, T §2·§3·§4)

**판정 원칙(D §2-1 D4, §6-3).** 저장 판정은 HTTP 결과로 한다. WS는 알림 경로다. Jarvis 결정(★)에 따라 T R3.1이 `client_message_id`를 전송 응답과 `message.created`에 넣었으므로, 「저장 여부 확인 중」의 **자동 해소를 기본 경로**로 하고 수동 「다시 시도」는 fallback으로 둔다(D §6-3 전이 4와 다른 점은 §8 I-3).

**대응 키:** 로컬 대기 항목과 서버 메시지의 일치는 `(conversation_id, author_id = 나, client_message_id)` 3개 값으로 판정한다. 이는 T §2의 멱등 unique key와 같다. `client_message_id` 단독으로 판정하지 않는다.

**전이 규칙(D §6-3 1–4 + Jarvis 결정)**

1. 「저장 확인」은 연결 상태로 되돌리지 않는다.
2. 「다시 연결 중…」(WS만 끊김)에서도 HTTP 전송을 그대로 보내고 HTTP 결과로 판정한다.
3. 전송 직후 작성기는 **즉시 비워지고** 본문은 「전송 중」 항목으로 옮겨진다. 늦게 온 ACK는 작성기를 건드리지 않는다.
4. 「저장 여부 확인 중」은 아래 중 하나가 일어날 때까지 유지한다. ① 대응 키가 같은 `message.created` 수신(자동, 기본 경로) ② 사용자의 「다시 시도」 결과 ③ 사용자의 로컬 삭제.
5. 같은 메시지가 HTTP 응답과 `message.created`로 두 번 와도 **항목은 1개**다. 대응 키(위)와 `change_id`로 중복을 제거한다(T §4).
6. 「전송 중」 상태에서 대응 키가 같은 `message.created`가 먼저 오면, 중복 행을 만들지 않고 항목에 "서버 커밋 이벤트 수신" 표식만 남긴다. 이후 HTTP가 응답 없이 끝나면 「저장 여부 확인 중」을 거치지 않고 「저장 확인」으로 간다. 이벤트만으로 「전송 중」을 즉시 「저장 확인」으로 바꿀지는 D4와 충돌하므로 **결정 필요(§8 Q-3)** — 결정 전 구현은 HTTP 응답을 기다린다.

**주의(자동 해소의 한계)**

- T R3.1은 `client_message_id`를 **전송 응답과 `message.created`에만** 명시했다. `GET /api/sync`·이력 응답 projection의 포함 여부는 T에 없다(§8 Q-2). WS가 끊긴 동안 커밋된 메시지는 catch-up으로 들어오므로, 그 항목은 자동 해소되지 않을 수 있다. 이때는 수동 「다시 시도」(멱등)가 fallback이다.
- 대기 항목은 **화면 메모리에만** 있다(P 원칙 2, T §6 오프라인 발신 큐 없음). 전체 새로고침·앱 종료 시 사라진다. 서버가 이미 저장했다면 새로고침 후 이력에 정상 메시지로 나타난다.

**MessageBody**(D §6-2 CMP-08, T §5): 텍스트 노드로만 렌더, HTML 미실행. 자동 링크는 `https`·`http`만, 그 외 스킴은 일반 텍스트. 링크 `rel="noopener noreferrer"`. 코드 블록은 `--font-mono`, `overflow-x: auto`. 한글 줄바꿈 `word-break: keep-all; overflow-wrap: anywhere;`(D §3-2). 고유 상태 없음.

### 5-3. ⚖️-D2 — UI 배너 조건과 TRD heartbeat의 관계

| 값 | 정본 | 누가 쓰나 | 효과 |
|---|---|---|---|
| WS heartbeat 25초 간격, 2회 연속 미응답 시 dead connection 정리 | T §7(제안값, 모바일 검증 전) | **서버**의 연결 정리 | 정리되면 클라이언트에는 WS close로 보인다 → C4 「다시 연결 중…」 |
| HTTP 네트워크 오류 연속 2회 | D §6-4(제안값) | **클라이언트** 배너 판정 | → C6 「연결이 끊겼습니다」 |
| `navigator.onLine` | D §6-4 | 클라이언트 | → C6 즉시 |

- 두 값은 **서로 다른 것을 판정한다.** heartbeat는 "WS가 살아 있나"(알림 경로), HTTP 연속 오류는 "서버에 닿나"(저장 경로)다. WS만 죽으면 「다시 연결 중…」이고 전송은 계속 HTTP로 판정한다.
- 최악의 경우 서버가 죽은 연결을 정리하기까지 약 50초(25초 × 2) 걸릴 수 있다는 것은 산술 추정이다. 그동안 클라이언트는 「연결됨」을 보일 수 있다. 클라이언트 측 heartbeat 감지(ping 송신·타임아웃)를 둘지는 정본에 없다 → §8 Q-13. 체감 정합은 `QA-FR-SYNC-07`에서 확인한다(D ⚖️-D2).
