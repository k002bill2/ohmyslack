# 결론

**방향 1: 자체 서버의 클린룸 Slack형 웹 메신저를 추천합니다.** MVP의 목적은 소규모 초대 팀이 채널·1:1 DM·스레드에서 대화하고 놓친 대화를 다시 찾을 수 있는지 검증하는 것입니다. Slack 전체 대체나 기존 워크스페이스 호환을 완료 조건으로 삼지 않습니다. 최종 결정은 영환님께 있습니다.

브리프의 잠정 MVP에서 **파일 업로드·전체 검색·presence를 v1으로**, Electron도 v1의 별도 승인 항목으로 내립니다. 웹에서 메시지 영속성·재접속·읽음 상태가 검증되기 전에는 기능을 추가하지 않습니다. 검색을 미뤄도 최근 이력의 페이지 탐색과 unread 위치 이동은 MVP에 남깁니다.

# 사실 / 추정 / 확인 필요

1. **사실 — 브리프에서 확인:** JS 529개 파싱과 partial 커버리지, 원격 웹앱 진입점, Electron 보안 설정이 기록되어 있습니다(E1). 이번에는 브리프와 요청문을 읽었으며 대상 앱을 실행하거나 분석하지 않았습니다.
2. **추정 — 제안의 전제:** 5–20명 규모의 초대 팀, 단일 워크스페이스, 데스크톱 브라우저 중심을 가정합니다. Slack 이력 이전과 기존 워크스페이스 연결은 첫 사용의 전제가 아니라고 가정합니다.
3. **추정 — 우선순위:** 파일·검색·presence를 미루면 저장·전달·읽음 상태에 집중할 수 있습니다. 반대로 실제 업무가 문서 공유·과거 검색 중심이면 이 MVP는 Slack 대체 수요를 검증하지 못할 수 있습니다.
4. **확인 필요 — 사용자 의도:** 자체 팀용 제품인지 기존 Slack 워크스페이스를 계속 쓰려는 것인지, 초대 방식과 계정 제공자, 파일·검색의 첫날 필수 여부를 영환님이 결정하셔야 합니다. API·약관·클린룸 경계는 A, 스택·정렬·복구 방식은 C의 결과가 필요합니다.
5. **확인 필요 — 일정:** 인력·기존 코드·인증 수단·배포 조건이 정해지지 않아 달력 일정은 제시하지 않습니다. 일정 산정은 아래 수용 기준을 작업으로 분해한 뒤 진행해야 합니다. 모든 수치 기준은 제안이며 성능 실측이나 통과 결과가 아닙니다.

## 2. 사용자 시나리오와 수용 기준 — 5개

아래는 구현 후 수행할 검증 계약입니다. 이번 토론에서 실행하거나 통과한 테스트가 아닙니다. 합성 계정 A/B/C와 더미 메시지만 사용합니다.

| 시나리오 | 동작 | 통과 기준 |
|---|---|---|
| S1. 초대받아 팀에 참여 | 관리자가 A/B/C를 초대하고 A가 로그인해 채널에 들어갑니다. 이후 C를 비활성화합니다. | 미초대 사용자는 이력을 읽거나 구독하지 못합니다. 비활성화된 C의 기존 세션·실시간 연결에서도 읽기·쓰기가 거부됩니다. 일반 멤버의 관리자 동작 요청은 거부됩니다. |
| S2. 채널에서 메시지를 주고받기 | A/B가 채널에서 한글·링크·코드 블록 메시지를 보내고 A가 본인 메시지를 수정·삭제합니다. | 한글 조합 중 Enter는 전송하지 않습니다. 저장 확인된 메시지가 새로고침·서버 재시작 후 남습니다. 재시도로 같은 요청을 3회 보내도 메시지는 1개입니다. B는 A의 메시지를 수정·삭제할 수 없습니다. |
| S3. 1:1 DM으로 연락하기 | A/B가 DM을 만들고 대화합니다. C가 DM ID를 알고 접근을 시도합니다. | C는 목록·이력·전송·실시간 구독의 어느 경로에서도 DM 내용이나 메시지 이벤트를 얻지 못합니다. A/B가 DM을 다시 열어도 동일 대화로 이동합니다. |
| S4. 스레드에서 멘션 확인 | A의 채널 원문에 B가 A를 멘션한 답글을 남깁니다. A가 답글로 이동하고 읽습니다. | 원문·답글 수·답글 순서가 일치합니다. 멘션은 한 번만 집계되고 해당 답글을 읽으면 해제됩니다. 채널 본문을 읽기만 하면 아직 안 본 답글의 스레드 배지는 남습니다. 원문 삭제 후에도 답글을 열 수 있습니다. |
| S5. 연결이 끊겨도 따라잡기 | B가 연결을 끊은 60초 동안 A가 100개 메시지를 보냅니다. B가 복귀해 이전 이력도 탐색합니다. | 복구 후 저장된 메시지가 누락·중복 없이 같은 순서로 보이고 unread가 일치합니다. 연결 단절 중 전송은 성공으로 표시하지 않습니다. 이미 저장된 메시지의 확인 응답만 유실된 경우에도 재시도가 중복을 만들지 않습니다. 1만 개 더미 메시지의 이전 페이지에서 경계 누락·중복이 없어야 합니다. |

### 공통 출시 게이트

1. **권한·렌더링:** 두 개의 더미 워크스페이스로 교차 접근 거부를 확인합니다. 제품 UI는 단일 워크스페이스여도 서버 격리 검증은 생략하지 않습니다. 메시지·프로필의 HTML/스크립트 문자열은 실행되지 않고 위험한 링크 스킴은 작동하지 않아야 합니다.
2. **정렬·읽음 계약:** 모든 클라이언트에 대화별 확정 순서를 제공합니다. 채널 unread는 원문, 스레드 unread는 답글을 대상으로 분리합니다. 읽음은 사용자가 실제 열어 본 마지막 위치까지 전진하며 새로고침·다른 세션에서도 유지됩니다. 본인 메시지는 unread/자기 멘션 집계에서 제외합니다. 삭제 메시지는 미읽음 수에서 제외하고 정렬 자리는 유지합니다. 구체적 모델은 C와 조율합니다.
3. **성능 제안:** 같은 테스트 환경에서 동시 연결 20개, 초당 메시지 5개를 10분 동안 보내 저장 확인부터 상대 UI 표시까지 p95 1초 이하를 목표로 합니다. 환경·전송량·실패율·측정 구간을 함께 기록해야 합니다. 공인 성능 보장은 아닙니다.
4. **복구·접근성:** 합성 데이터 백업을 격리된 새 DB로 복원해 메시지·DM 멤버십·읽음 위치를 대조합니다. 키보드만으로 공간 전환·전송·스레드 닫기와 포커스 복귀가 가능해야 합니다. 공용 인프라 볼륨 삭제는 허용하지 않습니다.
5. **사용성 파일럿:** 영환님이 선택한 3–5명이 3개 업무일 동안 사용하고 S1–S5를 수행합니다. 권한 누출·저장 확인 메시지 유실·복구 중 중복이 없어야 합니다. 빠진 검색·파일·앱 외부 알림 때문에 일상 대화를 완료하지 못하면 MVP 가설 실패로 기록하고 v1 우선순위를 재결정합니다. 이 파일럿은 Slack 완전 대체 검증이 아닙니다.
