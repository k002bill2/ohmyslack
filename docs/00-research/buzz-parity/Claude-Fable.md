### 2-3. 현재 구현에서 확인한 정합 문제 (기능 추가와 무관, 수정은 관찰 창 뒤)

1. **푸시 `Topic` 헤더에 대화 ID가 평문으로 나갑니다.** `topicOf`는 대화 UUID에서 하이픈만 뗀 값을 돌려주고(`apps/server/src/modules/push/sender.ts:41-44`), 전송 시 `topic`으로 넘깁니다(`apps/server/src/modules/push/service.ts:74-79`). payload는 암호화되지만 `Topic`은 push 서비스가 읽는 HTTP 헤더입니다(RFC 8030 §5.4). TM-PUSH-01은 payload만 다룹니다(`docs/08-security/THREAT_MODEL.md:221`). 영향은 작습니다(무작위 UUID, 사용자 1명). 그래도 "식별자를 외부에 평문으로 주지 않는다"는 원칙에 맞추려면 서버 비밀로 HMAC한 값으로 바꾸는 편이 낫습니다. → 결정 C-5.
2. **알림 제목이 코드명입니다.** 서비스 워커 고정 제목이 `ohmyslack`입니다(`apps/web/src/features/pwa/push-notify.ts:16-20`, `apps/web/src/ui/copy.ts:330-334`). manifest 이름은 「메신저」입니다(`apps/web/public/manifest.webmanifest:2-3`). 기계 검증은 manifest만 봅니다(`DESIGN_REFERENCE.md:64`). 개인 전용이라 위반은 아니지만 잠금 화면에 "slack"이 든 이름이 보입니다. → 결정 C-6.
3. **TM-BOT-06 서술이 구현과 다릅니다.** 위협 모델은 "승인은 해당 스레드 안에서만 유효(어댑터)", 테스트 `test_approval_only_owner_in_thread`라고 적습니다(`THREAT_MODEL.md:215`). 실제 어댑터는 `/approve`를 해석하지 않고 넘기며(`integrations/hermes-plugin/ohmyslack/adapter.py:3-6`), 테스트 이름은 `test_approve_text_passes_through_and_non_owner_approve_ignored`입니다(`integrations/hermes-plugin/tests/test_inbound.py:172-181`). 스레드 결속은 어댑터가 아니라 **Hermes 세션 키**가 합니다(DM 키에 `thread_id` 포함, `gateway/session.py:712-734`). 통제는 존재하지만 위치와 증거 이름이 문서와 다릅니다. "다른 스레드의 `/approve`는 승인하지 않는다"를 직접 확인하는 테스트는 ohmyslack 쪽에 없습니다.

## 3. 버튼형 승인(FR-BOT-07) 위협 모델

보호 대상은 AS-12 "Hermes 세션 지시 권한"(무결성 최상위, `THREAT_MODEL.md:46`)입니다.

### 3-1. 지금의 텍스트 경로 (사실)

1. owner 판정은 서버가 정한 `author_id`만 씁니다(`adapter.py:345-348`). 비owner `/approve`는 버립니다(`test_inbound.py:172-181`).
2. 스레드 결속은 Hermes 세션 키가 합니다(§2-3 3번).
3. **요청 결속은 없습니다.** `/approve`는 대기열 맨 앞(가장 오래된) 요청을 승인합니다(`approval.py:144-176`).
4. Jarvis 프로필의 승인 설정은 `mode: smart`, `timeout: 300`입니다(`~/.hermes/profiles/jarvis/config.yaml:426-428`). `smart`에서는 무해하다고 판단된 명령이 자동 승인되어 사람 승인이 드뭅니다(`qa/manual/QA-FR-BOT-06.md:16`).
5. 재연결 뒤 15분 안의 메시지는 다시 실행 대상이 됩니다(`adapter.py:41` `BACKLOG_LIMIT_SECONDS = 15 * 60`).

| APR-6 | **상태 불일치.** Hermes 대기열은 메모리에 있습니다(`approval.py:124`). 게이트웨이가 재시작하면 요청은 사라지는데 카드는 "대기"로 남습니다 | 카드의 최종 상태는 봇이 보고(승인됨·거절됨·만료·철회). 누름 직후는 "전달 중", 봇 확인 뒤에만 "승인됨" 표시(원칙 D4와 같음) |

| APR-8 | **잘못 누름.** 새 카드가 도착하며 목록이 밀려 손가락 아래로 승인 버튼이 들어옴 | 승인은 2단계(누름 → 명령을 다시 보여 주는 확인). 거절은 1단계. 승인 버튼에 기본 포커스·Enter 연결 없음 |
| APR-9 | **잠금 화면 승인.** 알림 동작 버튼으로 승인하면 기기 잠금 해제와 명령 확인을 건너뜁니다 | 알림에 동작 버튼을 달지 않음. 알림 payload에 명령·설명 미포함 |
| APR-10 | **권한 주체 혼동.** 봇이 채널에 참여하면(BOT_CHANNEL_SPEC) 다른 멤버도 카드를 봅니다 | 누름은 사람 세션(쿠키 + CSRF + Origin) + `user_id == 봇의 owner`일 때만. 봇 토큰으로 누름 불가. 승인 카드는 owner DM에만 게시하는 것을 기본으로 |
| APR-11 | **기록.** 누가 언제 승인했는지 남지 않거나, 반대로 명령 문구가 로그에 남음 | 누름 기록은 `request_id`·선택·시각·`user_id`만. 명령 문구는 로그·계측에 0(기존 로그 허용목록 규칙) |
| APR-12 | **텍스트 경로 회귀.** 버튼이 생기며 텍스트 승인이 막히거나 달라짐 | 텍스트 `/approve`·`/deny`는 그대로 동작. 텍스트로 해결된 요청의 카드는 "승인됨/거절됨"으로 닫힘 |

### 3-3. 판단

- 버튼이 줄이는 위험: 요청 결속 부재(§3-1 3번).
- 버튼이 늘리는 면: 새 테이블·라우트·WS 이벤트·UI 상태 7종(§5-1).
- 변하지 않는 것: XSS 1건 또는 잠금 해제된 기기가 곧 승인 권한이라는 점. 텍스트 경로에서도 같습니다.

## 4. 그 밖의 후보별 위협 영향

### 4-1. 알림 payload 개인정보

- 현재: payload는 식별자 6개 필드만(`apps/server/src/modules/push/service.ts:111-118`, `push-notify.ts:22`), 문구는 고정입니다. TM-PUSH-01과 일치합니다.
- 원칙(새 기능 공통): payload에 **본문·대화 이름·작성자 이름·파일명·검색어·명령 문구·반응 이모지**를 넣지 않습니다.
- iOS는 표시 없는 push를 허용하지 않습니다(`push-notify.ts:4`). 따라서 **반응·처리 상태·입력 중은 push를 보내지 않습니다.** 보내면 내용 없는 알림이 매번 뜹니다.
- 승인 요청은 300초 안에 답해야 하므로 알림 가치가 있습니다. `kind`에 `approval`을 추가하고 고정 문구(§5-2)만 쓰는 안을 결정 후보로 둡니다(C-3). 명령은 싣지 않습니다.

### 4-2. 일반 문서 첨부 (FR-OPS-09)

현재 통제(사실): 내용으로 형식 판정(`apps/server/src/modules/attachments/service.ts:49-53`), 응답 `nosniff`·`no-store`·`Content-Disposition: inline`(`routes.ts:94-102`), 첨부 전용 CSP `sandbox; default-src 'none'`(`routes.ts:39,113-117`), 형식 4종 CHECK(`apps/server/migrations/0003_attachments.sql:20`).

문서를 추가하면 달라지는 점:

1. **파일명이 처음 생깁니다.** `attachments`에 파일명 컬럼이 없습니다(`0003_attachments.sql:5-21`). 문서는 파일명이 필요합니다. 요구: 경로 구분자·제어 문자 제거, 길이 상한, 응답 헤더는 `filename*=UTF-8''…` 퍼센트 인코딩(RFC 6266)으로만 넣어 헤더 주입을 막음. 파일명은 로그·push에 넣지 않음.
2. **`inline`이 기본값입니다.** 문서 형식은 반드시 `attachment`로 분기해야 합니다(PRD "다운로드 전용", `PRD.md:126`). 형식별 분기 누락을 테스트로 고정합니다.
3. **텍스트 파일은 매직 바이트가 없습니다.** 판정 규칙을 새로 정해야 합니다: 유효한 UTF-8 + NUL 없음일 때만 `text/plain; charset=utf-8`. HTML·SVG·스크립트로 판정되는 내용은 거부 유지.
4. **ZIP 기반 문서(docx·xlsx)는 1차 범위에서 제외를 권합니다.** 컨테이너 안을 검사하지 않으면 형식 위장을 구분할 수 없습니다. 1차는 PDF + 텍스트(md·txt·csv·json)로 좁힙니다.
5. **간접 프롬프트 인젝션 면이 넓어집니다.** 지금 어댑터는 사람이 올린 이미지만 Hermes에 넘깁니다(`adapter.py:387-390`). 문서를 넘기기 시작하면 문서 안의 지시문이 Jarvis 입력이 됩니다(TM-BOT-05 확장, `THREAT_MODEL.md:214`). 1차는 **봇 → 사람 방향만** 열고, 사람 → 봇 문서 전달은 별도 결정으로 둡니다.
6. iPhone 홈 화면 앱에서 `attachment` 응답이 실제로 저장·열기까지 되는지는 실기 확인이 필요합니다(확인 필요 2).

### 4-3. 검색 (FR-OPS-06)

1. **강조 표시가 XSS 경로가 됩니다.** PostgreSQL `ts_headline`은 일치 부분을 태그로 감싼 문자열을 돌려주며, 공식 문서가 "웹 페이지에 그대로 넣기에 안전하지 않다"고 경고합니다(https://www.postgresql.org/docs/current/textsearch-controls.html, "Cross-site Scripting (XSS) Safety"). 요구: 서버는 **원문 조각 + 일치 위치(오프셋)** 만 돌려주고, 웹은 텍스트 노드로 그립니다. 서버가 만든 HTML을 그리지 않습니다.
2. 검색어는 로그·계측·URL 쿼리에 남기지 않습니다(B와 같음). 주소에 검색어를 넣으면 Serve 접근 로그에 남으므로(TM-LOG-03) 검색어는 요청 본문 또는 메모리 상태로만 둡니다.
3. 삭제·수정된 메시지가 결과에 다시 나오지 않아야 합니다(TM-WS-06과 같은 종류).

### 4-4. 처리 상태·입력 중 (FR-OPS-07 일부)

- 처리 상태 frame은 봇 토큰 경로로만 발신하고, 서버가 `author_kind = bot`을 붙입니다. 사람 계정이 "Jarvis 처리 중"을 만들 수 없어야 합니다.
- Hermes는 2초마다 `send_typing`을 부릅니다(D의 X5). 서버는 수신 frame에 TTL을 두고, 끊기면 표시를 스스로 내립니다. "처리 중"이 영원히 남는 것이 가장 흔한 실패입니다.
- DB·sync·push를 쓰지 않습니다(B와 같음).

### 4-5. 기기 세션 화면 (FR-AUTH-04)

- `sessions`에는 기기 정보가 없습니다(`apps/server/migrations/0001_initial_schema.sql:44-55`: 생성·마지막 사용·만료·폐기 시각만). 화면에 "iPhone"이라고 보여 주려면 새 컬럼이 필요합니다.
- 위협 모델은 로그에 IP·UA 0건을 요구합니다(`THREAT_MODEL.md:42`). 원시 User-Agent·IP를 저장하지 말고, 로그인 시 한 번 만든 **거친 라벨**(예: "iPhone · Safari")만 저장하는 안을 권합니다(C-4).
- 원격 종료는 기존 CSRF + Origin 통제를 그대로 탑니다. 현재 세션은 목록에서 구분 표시하고, "다른 기기 모두 종료"는 확인 1단계를 둡니다.
