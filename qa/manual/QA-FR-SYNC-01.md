## (b) 측정 절차 (같은 맥, 같은 시계)

전제: 서버·DB·브라우저가 모두 같은 맥에서 돌아 시계가 같다. 웹 클라이언트 **측정 빌드**가 필요하다(W-10k C에서 구현 — `VITE_LATENCY_PROBE=1`, 요약은 `window.__omsLatency.summary()`, 아래 "웹 측정 빌드 요구사항").

1. 테스트 DB(`ohmyslack_test`)만 쓰는지 확인한다: `set -a; . ./.env.test; set +a` 후 `tsx tools/bin/assert-test-db.ts` 종료 코드 0.
2. 웹 측정 빌드를 만든다: `pnpm --filter @ohmyslack/web build:measure`(산출물 `apps/web/dist-measure`, 없으면 다음 단계가 즉시 실패한다). 같은 맥에서 `PERF_OBSERVER_WAIT_S=300 pnpm perf:latency`(20연결·합계 5msg/s·10분)를 시작한다. 하네스는 격리 스키마·임의 포트 서버(측정 빌드를 같은 출처로 서빙하고 그 주소 `http://127.0.0.1:<port>`를 허용 출처로 둔다)·부하 채널을 만든 뒤 콘솔에 `관측 준비: 서버 <주소> · 계정 observer@example.test · 채널 <id>`를 출력하고 300초 동안 부하를 멈춰 둔다(접속 정보는 디스크에 남기지 않음).
3. 그 300초 안에 ego-browser 1개로 출력된 서버 주소를 그대로 열어(측정 빌드 웹 클라이언트가 같은 출처로 뜬다) `observer@example.test`(테스트 비밀번호)로 로그인하고 출력된 채널을 연다(전경, 탭 활성, 창 가림 없음). 관측 브라우저는 21번째 연결이며 (a) 집계에는 포함되지 않는다. 준비가 늦으면 중단하고 대기 시간을 늘려 다시 시작한다.
4. 부하 중 브라우저 탭을 전경으로 유지한다(백그라운드 탭은 rAF가 멈춰 측정이 무효).
5. 부하 종료 후 측정 빌드의 메모리 히스토그램 요약(p50·p95·p99·max·표본 수)만 읽어 기록한다. 메시지 ID·본문은 기록하지 않는다.
6. 같은 구간의 (a) 결과 파일 `reports/perf/latency-<timestamp>.json`에서 p50·p95·표본 수·오류율·누락·중복·환경을 옮긴다.
7. 판정: (b) p95 ≤ 1000ms이고 ②·③을 만족하면 `PASS`. 하나라도 어긋나면 `FAIL`과 원인 기입.

### 웹 측정 빌드 요구사항(이 문서 범위 밖, 웹 레인 작업)

- 측정 빌드 플래그에서만 켜진다(운영 빌드에는 코드 경로 없음).
- `message.created` 수신 → 해당 항목이 DOM에 그려진 뒤 `requestAnimationFrame` 콜백 시점의 `Date.now()` − 메시지 `created_at`을 **메모리 히스토그램**에만 누적한다.
- 상관용 메시지 ID는 메모리에서만 쓰고 디스크·로그·계측 전송에 남기지 않는다(PRD §10, PRD:171).
- 요약(p50·p95·p99·max·표본 수)을 읽을 수단(예: 측정 빌드 전용 콘솔 함수)만 노출한다.
